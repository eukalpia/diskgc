## Зачем

Диски разработчиков заполняются тем, что никто не просил хранить: каталоги `target/` в Cargo, которые за два дня вырастают на 100 ГБ, `node_modules` веток, которые вы забросили в июле, кэши сборки Go, которые пересоздаёт каждый запуск тестов, контейнеры, оставшиеся после прерванных тестов, временные каталоги AI-агентов для программирования. macOS называет всё это «System Data» и не предлагает помощи; `du` показывает *где*, но не *что безопасно удалить*.

diskgc работает как небольшой демон: следит за свободным местом и его динамикой и удаляет только то, что инструмент может восстановить заново — с объяснением каждого действия, планом, который можно прочитать до того, как что-либо произойдёт, и историей того, что было освобождено.

## Ключевые особенности

- **Объясняет себя.** Каждое действие сопровождается причиной: *"target is 105 GB (> 40 GB cap): everything older than a day"*, *"project untouched for 30 days; restored by install"*.
- **Знает проекты, а не только папки.** `target/` находится по содержимому, каталоги сборки — только рядом с маркером проекта, а активность оценивается по всему проекту (git worktree считается отдельным проектом).
- **Действует до того, как диск заполнится.** Прогноз по последним шести часам заранее повышает уровень очистки; пороги ужесточаются от *normal* к *low* и далее к *critical*.
- **Не трогает важное.** Исходники, `.git`, базы данных и истории чатов никогда не становятся кандидатами; исключённые глобы никогда не затрагиваются; логи сжимаются на месте, а не удаляются.
- **Находит причину.** `diskgc stats` показывает прирост по дням и категориям и пути, которые постоянно возвращаются — места, которые нужно исправить, а не просто очистить.
- **Терминальная панель и JSON.** Шестиэкранный TUI и `--json` в каждой команде для скриптов.

## Быстрый старт

```sh
cargo install --locked --git https://github.com/eukalpia/diskgc diskgc
diskgc config --edit      # укажите в [scan] roots каталоги, где лежат ваши проекты
diskgc plan               # что удалит очистка и почему — ничего не трогается
diskgc install            # запустить демон при входе в систему (launchd / systemd --user / Task Scheduler)
diskgc status
```

Готовые бинарники для macOS (Apple Silicon, Intel), Linux (x86_64) и Windows (x86_64) прикреплены к каждому [релизу](https://github.com/eukalpia/diskgc/releases): распакуйте `diskgc` (и при желании `diskgc-ui`) в любой каталог из `PATH`.

## Что очищается

| Правило | Что | Когда |
|------|------|------|
| Rust-сборки | каталоги `target/` (находятся по содержимому, где бы они ни были) | артефакты не менялись 7 дней; выше 20 ГБ — также инкрементальные кэши и «толстые» тестовые бинарники; выше 40 ГБ — всё старше суток; общий бюджет 40 ГБ для всех `target/` вместе |
| node_modules | `node_modules` рядом с `package.json` | в проекте ничего не менялось 30 дней |
| Каталоги сборки | `.dart_tool`, `build`, `_build`, `.next`, `.turbo`, `__pycache__`, `.gradle`, … рядом с маркером проекта | то же правило 30 дней |
| Временные каталоги | Временные папки сессий Claude Code, ваши записи в системном каталоге временных файлов, устаревшие рабочие каталоги в пользовательском `$TMPDIR` (macOS) | без изменений 3 дня / 7 дней / 24 ч |
| Инструменты ИИ | старые версии приложения Codex, брошенные установки runtime | всегда (хранятся текущая + 1) |
| Docker | осиротевшие testcontainers, остановленные контейнеры, висячие тома и образы, кэш сборки | 2 ч / 24 ч / 7 д |
| Кэши инструментов | кэши Go, npm, uv, pnpm и sccache сверх лимита, остатки обновлений Chrome и VS Code, загрузки Homebrew, DerivedData Xcode, кэши симуляторов и шейдеров Metal | лимиты по каждому правилу |
| Холодные файлы | логи сессий и JSONL-истории Codex и Claude Code | **сжимаются** файловой системой (APFS, NTFS), никогда не удаляются |

## Как принимается решение

Демон просыпается каждые 10 минут и проверяет свободное место:

| Свободное место | Поведение |
|------------|-----------|
| выше `comfortable_gb` (150) | плановая очистка каждые 6 часов |
| ниже `comfortable_gb` | очистка сейчас, по обычным окнам |
| ниже `low_gb` (100) | уровень *low*: все окна давности уменьшаются вдвое |
| ниже `critical_gb` (60) | уровень *critical*: окна уменьшаются вчетверо, лимиты размера — вдвое |

Аппроксимация методом наименьших квадратов по снимкам за последние шесть часов прогнозирует свободное место через 24 часа; если прогноз пересекает порог, демон заранее повышает уровень очистки. Каждый запуск записывается, поэтому `diskgc stats` показывает прирост по дням и категориям, а также постоянных «нарушителей».

## Безопасность

diskgc удаляет файлы — в этом его задача, — поэтому он устроен так, чтобы его поведение было предсказуемым:

- Он предлагает только то, что инструмент может восстановить (результаты сборки, каталоги зависимостей, кэши, временные файлы), и указывает причину для каждого действия; `plan` и `clean -n` показывают этот список, ничего не трогая.
- Исходники, `.git`, базы данных и истории чатов никогда не становятся кандидатами; всё, что попадает под `[scan] exclude`, не трогается; исполнитель отказывается работать с любым путём вне `[safety] allowed_prefixes` (по умолчанию — ваш домашний каталог и системные временные и кэш-папки).
- `[safety] delete_mode = "trash"` перемещает файлы в корзину вместо окончательного удаления (macOS и Linux; если корзина на другом томе, используется удаление).
- Каждый запуск записывается в журнал (`diskgc history`) с тем, что было запланировано и что реально освобождено.

Он всё равно работает без присмотра с вашими правами, поэтому перед установкой демона прочитайте первый `plan` на своей машине.

## Терминальная панель

`diskgc ui` открывает панель, построенную на [Cinder](https://github.com/eukalpia/cinder), которая общается с демоном по своему [IPC-протоколу](../PROTOCOL.md):

| Экран | |
|--------|---|
| **Overview** | свободное место, уровень, прогноз, куда уходит место |
| **Plan** | каждое предложенное действие с причиной — снимите отметку с того, что нужно оставить, выполните остальное или запустите «сухой прогон» |
| **Report** | самые крупные нарушители по категориям |
| **History** | запуски, прирост по дням, постоянные нарушители |
| **Memory** | RAM по программам, осиротевшие вспомогательные процессы |
| **Log** | живая активность демона |

```
1-6 / tab   switch screens        r   refresh the current screen
p           build a plan          space / enter   toggle the highlighted action
x           execute selected      n   dry run             a   toggle all
k           terminate orphaned helper processes (Memory)   q   quit
```

Панель — отдельный нативный исполняемый файл (`diskgc-ui`); `diskgc ui` находит его рядом с `diskgc` или в `PATH` и запускает демон, если он не запущен.

## Команды

```
diskgc report            что занимает диск: категории и самые крупные нарушители
diskgc plan              что сделает очистка, с причинами — ничего не трогается
diskgc clean [-n]        очистить сейчас (-n = только план)
diskgc status            состояние демона, свободное место, прогноз, последний запуск
diskgc stats             прирост по дням, тренды по категориям, постоянные нарушители
diskgc history           последние запуски и что они удалили
diskgc mem               RAM по процессам, осиротевшие вспомогательные процессы (--kill-orphans)
diskgc install | uninstall
diskgc config [--edit|--show]
diskgc ui                терминальная панель
```

Каждая команда принимает `--json`.

## Конфигурация

`~/.config/diskgc/config.toml` (Linux, macOS) или `%APPDATA%\diskgc\config.toml` (Windows) создаётся с настройками по умолчанию при первом запуске и перечитывается демоном на каждом тике. Каждый ключ описан в [docs/CONFIG.md](../CONFIG.md). Основное:

```toml
[scan]
roots = ["~/work", "~/src"]          # где лежат ваши проекты
exclude = ["~/work/keep-forever/**"] # глобы, которые никакое правило не должно трогать

[thresholds]
comfortable_gb = 150
low_gb = 100
critical_gb = 60

[safety]
delete_mode = "permanent"            # или "trash"
```

## Платформы

| Платформа | Статус |
|----------|--------|
| macOS (APFS) | используется ежедневно; основная цель |
| Linux | тестируется в CI и в контейнерах; автозапуск через `systemd --user` |
| Windows | собирается и проходит тесты в CI; автозапуск через Task Scheduler — наименее проверенная часть, отчёты приветствуются |

Прозрачное сжатие доступно на APFS и NTFS. Матрица платформ — в [docs/ARCHITECTURE.md](../ARCHITECTURE.md).
